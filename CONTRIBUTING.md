# Contributing

Thanks for taking a look. Issues and pull requests are both welcome.

If you are new to Git, GitHub or VS Code, [GETTING_STARTED.md](GETTING_STARTED.md)
walks through the whole setup and the everyday workflow. This file covers the
conventions this project follows.

## Getting set up

```bash
python -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\Activate.ps1
pip install -e ".[data,dev]"
pytest -q
```

## Before you open a pull request

```bash
pytest -q          # the tests pass
ruff check .       # the style is consistent
```

Both of these also run automatically on your pull request, so a red cross on
GitHub usually means one of them was skipped locally.

## What makes a good change here

**Keep it focused.** One idea per pull request. A change that fixes a bug *and*
renames some things *and* adds a feature is three pull requests, and much harder
to review than three separate ones.

**Write the test first if you can.** A test that fails before your change and
passes after it is the clearest possible evidence that the change did what you
meant.

**Say what changed and why in the commit message.** "Add last-quarter goals as a
feature" tells a reader something; "update" does not.

## If your change affects the model

The point of this project is predicting well, so a change to the model needs
evidence, not just a passing test suite.

Run the backtest before and after, and put both sets of numbers in the pull
request description:

```bash
brownlow backtest --train 2015-2023 --test 2024-2025
```

For anything more than a small tweak, cross-validate instead — six folds is much
harder to fool than one season:

```bash
brownlow cv --min-train 5
```

A change that makes the metrics slightly worse is still worth discussing if it
makes the model simpler or more interpretable. Just say so, rather than leaving a
reviewer to discover it.

If you added a new experiment config, run it and commit the regenerated
`docs/index.html` alongside it, so the published page matches the code:

```bash
brownlow run experiments/your-idea.json --seasons 2015-2026
```

## Style

- Ruff enforces the formatting; run `ruff check .` and it will tell you.
- 100-character lines.
- Type hints on public functions.
- Docstrings that explain **why**, not just what. The code already says what it
  does; the useful comment is the reason it does it that way, or the trap it is
  avoiding.
- Prefer clear names over short ones.

## Tests

Tests live in `tests/`, one file per module. They use synthetic data generated by
`brownlow.synthetic`, so the suite runs anywhere without downloading anything.

Because the synthetic seasons are generated from known weights, you can test that
the model *recovers the right answer* rather than only that it runs without
raising. `tests/test_model.py` has examples of both.

## Reporting a bug

Open an issue with the command you ran, what you expected, what happened, and the
full error message. `.github/ISSUE_TEMPLATE/bug_report.md` prompts for all of it.

## Suggesting a model improvement

Use the **Model idea** issue template. It asks which metric should move and by
roughly how much — worth deciding before you run the experiment, so the result
means something either way.

The [Known limitations](README.md#known-limitations) section of the README is a
good place to look for things that need doing.
